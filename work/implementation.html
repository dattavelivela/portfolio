Implementation Builder: taking customer setup off the engineering queue

Aug 20268 min read

Every new Procol customer has to be set up before they can buy anything: which modules they get, who approves what, what their request forms look like, what happens when a bill doesn’t match its order. None of that had a screen. Engineers did it by running scripts, one customer at a time.

I mapped how setup really worked across our backend and dashboard, wrote the case for one builder that sits on top of the engines we already had, and built a working prototype of it with Claude Code: an automation canvas and an intake type wizard that turn what an admin draws into the exact records our backend already runs.

Context

Before a customer buys anything, someone sets Procol up

Procol runs the whole buying process for large companies, from the first request to paying the supplier. Every company runs that process differently: different approvers, different forms, different rules for when an invoice can be paid.

So every new customer goes through implementation: copying a standard setup into their account, switching on modules and permissions, creating their request types, wiring approvals, and adding whatever is special about them. Today almost every one of those steps is a script an engineer runs.

Why it is a problem

Every new customer waited on engineering

Because setup lived in scripts, the people who owned onboarding couldn’t change anything themselves. A new request type, a new approval condition or a customer’s quirk became an engineering ticket, and some of them became a code deploy.

That slowed onboarding, pulled engineers off the product, and meant customers couldn’t adjust their own setup after go-live.

Business goals

What the business needed

Let customer admins and our implementation team set up and change Procol themselves, without a script or a deploy.

Insights

What reading the whole system taught us

Before designing anything I mapped the backend and the dashboard end to end: the sourcing and purchase lifecycles, the approval engine, the workflow and automation engines, the data layer and every config-driven screen. That became eleven documents and a machine-readable spec.

Procol already had four engines that run business logic. The missing piece was a way to author them.

Some advertised options did nothing: only 3 of 10 documented trigger operators were ever evaluated.

19 code templates had customer names baked in. Each new behaviour meant a deploy.

Creating one intake type meant a script that touched a form, a condition, a workflow and a shared approval list.

Admins could build approval flows, but only on conditions an engineer had seeded first.

Good patterns already existed in pieces: a metadata-driven builder, a canvas with draft and publish, an AI generate-and-review loop.

The real problem

Not missing engines, missing authoring

The platform could already do most of what customers asked for. What it couldn’t do was let anyone outside engineering describe it.

  • Setup was a runbook, not a product. Copy the standard pack, enable modules one by one, set permissions, run the intake script, seed approval conditions, set up versioning, then run the customer’s own script.
  • Customer quirks became code. When a behaviour didn’t exist, the answer was a new hardcoded template, named after the customer.
  • Nothing told you what was real. Options that looked supported silently did nothing, so even engineers had to read the code to know.

Key decisions

The calls that shaped it

  • 🧱Don’t build a fifth engine.The builder is one authoring layer that compiles onto the approval, automation, workflow and rules engines we already run. Runtime risk stays where it’s understood; the new value is one place to author, version and review.
  • 👩‍💼Built for customer admins.Not only for our implementation team. That decision drove everything else: guardrails, plain labels instead of internal names, and nothing in the palette that could break another tenant.
  • ✅Only show what actually works.Every capability in the spec carries a status: implemented, partial or dead. The palette shows implemented ones only, so an admin can’t build a flow that silently does nothing.
  • 📏Conditions go through the rules engine.The automation engine’s own condition operators were mostly unwired. Rather than promise them, every condition an admin draws compiles to the rules engine, which already logs and isolates failures.
  • 🛑Fix the foundations first.Before admins touch anything: close a tenant-scoping gap, isolate failing actions, add approval flow priority and sign email approvals. These went into the proposal as blockers, not nice-to-haves.

Solution

Draw it once. Procol runs it the way it already does.

Automation canvas

Admins build a flow from triggers, rules, approvals and actions. Edges out of a rule or an approval label themselves success, failure, approved or rejected. The example is a guard most customers ask for: when a bill is submitted, check it against the order and receipt; if it matches, send it for approval; if not, put it on hold and tell accounts payable.

Publishing doesn’t interpret the drawing at runtime. It compiles it into the same records engineers write by hand today, and remembers what it created so a flow can be rolled back or uninstalled cleanly.

Intake type builder

Creating a new kind of request used to be one script touching four places. Now it’s a five-step wizard: basics, form, approval, workflow and review.

Where the engine has limits, the wizard says so instead of hiding them. Workflow selection only offers the one variable the backend actually reads today.

Clara drafts, the admin decides

The spec doubles as Clara’s vocabulary. An admin describes what they want, for example “when a bill fails 3-way match by more than 5%, notify the buyer team and put it on hold”, Clara drafts the flow, the admin reviews the difference and applies it. The same loop already worked in Procol’s RFP generator, so the pattern was proven.

What we didn’t build

Left out on purpose

  • No custom code for admins. The code escape hatch stays internal. Anything a customer needs becomes a proper, reusable action instead.
  • No loops, parallel joins or long timers in v1. The engines don’t support them safely yet, so the builder doesn’t pretend to.
  • No raw expressions by default. Admins pick from structured conditions; free-form expressions sit behind a permission and are validated before saving.

Where it stands

A proposal and a working prototype

The analysis, the design and the prototype went to the team together, with four product questions still open:

  • Where to start. Approvals only, or bill-matching automations, the most scripted and highest-value area today.
  • One builder or two. Whether our implementation engineers get a wider palette in the same builder or a separate internal mode.
  • Who owns the canvas. It lives in a shared UI kit owned by another team today.
  • What happens to the 441 scripts. Freeze and wrap them, or let Clara convert them into editable flows over time.

What I learned

What I’d take into the next product

  • 🔍Read the system before drawing it.The best design decision here came from research, not a canvas: realising the engines already existed and only authoring was missing.
  • 🤝Honesty is a feature.Showing only what works, and saying where the engine stops, builds more trust with admins than a bigger palette that sometimes does nothing.
  • ⌨️A prototype settles arguments.A canvas that compiles to real records answers “is this feasible?” faster than any document can.
